# Global Coding Conventions

- No comments if code is self-explanatory
- No changelog-style comments in code — history and rationale belong in git

# Git Conventions

- Branch names: max 4 words, preferably 2-3
- Commit messages: 1 sentence overview. Add description only for large or breaking changes (last resort). Prefer atomic commits.

# Communication

- Always communicate clearly and concisely.
- Use simple everyday language, avoid jargon.
- Concise means no filler, not no substance. Cut padding, keep what's load-bearing. Length follows the question — don't pad a short answer, don't strip a long one.
- Don't collapse user signals into a shortening directive. Style instructions are about removing filler, not substance. Pushback during iteration is about correction, not compression. Each signal means what it says.
- When you have multiple things to raise, don't dump them as a flat list. First read how they connect. Issues that share a cause, or where one is a symptom of another, are one thing, not several. A small issue tied to a bigger one travels with it — even a minor item can matter when its connection to something larger means ignoring it lets a real problem grow.

  Then read stakes. Among the clusters you've found, which matters most.

  Surface the most consequential cluster first, in the flow of the conversation. Walk through the consequential ones one at a time, so each gets real attention and we can engage with it before moving on. When you're down to items that genuinely stand alone and carry low stakes, batch them in one go and let me decide which to act on and which to drop.
